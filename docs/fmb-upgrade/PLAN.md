# Openinbox 相依套件與執行環境分階段升級計畫

## 目的與限制

本文件規劃未來的評估及升級工作，不代表已執行任何升級。依本任務範圍，**本次不改既有程式、安裝腳本、測試或 CI workflow，也不修改任何環境設定**。

計畫遵守下列原則：

- 核心維持 Python 標準函式庫及不需 pip 的安裝方式，除非 BOB 明確核准改變產品相依原則。
- 不連線到正式郵件、Agent、帳號或其他外部服務；整合測試使用 mock、本機假服務與虛構資料。
- 不讀取、複製或輸出任何真實憑證、郵件內容或私人資料。
- 涉及 SQLite 結構變更時，必須先驗證備份與還原，再進行升級。
- 每階段獨立審核、獨立回退；未通過驗收不得進入下一階段。
- 不在本計畫中變更 `.github/workflows`；未來若要擴充 CI 版本矩陣，另行取得授權並開獨立變更。

## 建議目標

- **Python**：把最低支援版本從 3.9 提高到至少 3.11，並以最低支援版本和一個較新的受支援版本建立驗證矩陣。Python 3.11 是建議起點，並非已核准的最低版本；若部署環境要求不同版本，先由 BOB 決策。
- **Python 套件**：除非盤點證明必要，維持不新增第三方執行期套件。
- **SQLite**：先量測實際版本及 FTS5 可用性，保留 `LIKE` 後備；不因本計畫任意提高 SQLite 最低版本。
- **時區資料**：明訂支援環境取得 IANA 資料的方式；暫不新增必要 pip 套件。
- **Node.js／npm**：維持為可選開發工具，而非執行期需求。
- **外部 CLI**：由各整合分開治理，不把 CLI 版本升級混入 Python 或應用程式核心升級。

## 共通驗證與回退要求

每階段都應記錄實際執行的版本、作業系統、測試命令、結果及未覆蓋項目。測試只能使用本機資料副本或 `tempfile`／`tmp_path`，不得碰正式帳號、正式資料或 repo 外路徑。

若某項升級不涉及資料格式變更，回退以還原前一版程式／文件與原執行環境為主。若涉及 SQLite schema 或資料轉換，須額外保留已驗證且受檔案權限保護的升級前備份，並演練還原；不得把直接複製執行中的 SQLite 主檔當成已驗證的備份策略。

## 階段 0：建立基線與升級前檢查

### 變更

- 在受控的開發環境記錄 Python、`sqlite3.sqlite_version`、FTS5 可用性、作業系統、Shell、時區資料狀態，以及已安裝的選用 CLI 版本。
- 盤點各部署環境現有 Python 版本與作業系統；只記版本與功能狀態，不記環境變數值、帳號設定或資料內容。
- 檢查測試是否真的可在預定最低 Python 版本執行，並找出使用到版本限定語法或標準函式庫行為的位置。
- 確認現有資料庫備份與復原流程，列出目前 schema 的升級／回退需求。
- 取得 workflow 目前使用的 Python／作業系統版本資訊，供後續決策參考；本階段不修改 workflow。

### 相容性風險

- 不同 Python 建置可能附帶不同 SQLite 版本或 FTS5 能力。
- 只測最新版會漏掉最低版本相容性問題；只測最低版本則可能漏掉新執行環境問題。
- CLI 版本查詢方式不一致；若版本輸出可能包含敏感資訊，應只擷取必要版本欄位。

### 驗證方式

- 使用本機命令取得版本與能力資訊，不發出外部服務請求。
- 在既有支援環境執行 `python3 -m unittest discover -s tests` 和 `scripts/smoke.sh`，記錄測試是否通過及必要工具缺席造成的跳過項目。
- 用虛構測試資料確認 FTS5 可用與不可用時都能得到正確搜尋結果。
- 檢查文件所宣告的 Python 版本與安裝腳本檢查一致。

### 回滾方式

- 本階段只產生盤點結果，不改執行環境或資料；若檢查失敗，停止升級計畫並保留基線紀錄，不需要還原程式或資料。

### 階段出口

- 有可重現的執行環境清單、測試基線與資料庫回退方案。
- 已確認實際部署 Python 版本；若仍有 Python 3.9 環境，先規劃遷移或取得 BOB 對停止支援的決策。

## 階段 1：Python 最低版本調整

### 變更

- 若 BOB 核准建議目標，將專案最低 Python 版本提升至 3.11，並同步更新安裝檢查與雙語文件中的版本宣告。
- 保持核心標準函式庫設計；不順便重寫程式、不更新選用 CLI、不改 SQLite schema。
- 在獨立工作中建立「最低支援版本＋較新受支援版本」的測試矩陣。若需修改 CI workflow，先取得明確授權並另案處理；本任務及本階段文件本身不修改 workflow。
- 在新增的最低版本執行完整測試，確認套件載入、型別註記、日期／時區、SQLite 與啟動流程都可執行。

### 相容性風險

- 使用 Python 3.9 的使用者將無法再通過新版安裝檢查，需先升級 Python 或保留舊版程式。
- 標準函式庫在不同 Python 版本間可能有行為差異；不能只用語法檢查代替完整測試。
- Python 版本更新可能連帶改變 SQLite 版本，需分辨失敗來自 Python 還是 SQLite 能力。

### 驗證方式

- 在目標最低 Python 版本及較新版本分別執行完整 `unittest` 與 `scripts/smoke.sh`。
- 確認安裝檢查拒絕低於支援版本的直譯器，且錯誤說明明確。
- 在隔離資料目錄啟動伺服器並測試健康檢查、示範資料、搜尋後備與 MCP stdio；不得載入 live 帳號設定或外部憑證。
- 比較兩個 Python 版本下的主要 API 與 SQLite 測試結果。

### 回滾方式

- 若新版尚未需要新資料格式，回退程式碼與版本宣告至前一版，讓使用者以原支援的 Python 版本執行。
- 若升級已要求使用者更新 Python，回退公告必須列出可用舊版程式與其 Python 需求；不得假設使用者可直接降回 Python 3.9 而仍獲安全支援。
- 不以未經批准的 workflow 修改作為回退前提。

### 階段出口

- 最低與較新 Python 版本均通過完整測試。
- README、安裝檢查與支援政策一致。
- 已確認仍使用舊 Python 的部署者有遷移方案或已接受停止支援。

## 階段 2：SQLite、FTS5 與時區資料相容性

### 變更

- 建立 SQLite 執行期診斷，記錄 SQLite 版本及 FTS5 是否可用，不輸出使用者資料。
- 明確保留 FTS5 不可用時的 `LIKE` 後備；若將來要規定最低 SQLite 版本，先提出效能與平台證據，再獨立決策。
- 記錄支援平台取得 IANA 時區資料的方式；優先使用平台套件或作業系統資料，不直接加入必要 pip 相依。
- 若發現 schema 遷移需求，另行定義版本化遷移、交易邊界、資料驗證與復原程序。

### 相容性風險

- FTS5 查詢語法、排序或索引行為可能因 SQLite 版本不同而有差異。
- `LIKE` 可保正確性但大資料集效能較低。
- 時區資料更新可能改變未來日期的時間換算；系統或容器若缺少資料，部分行事曆操作可能失敗。
- schema 遷移失敗可能造成資料不可讀；禁止把應用程式回退視為足以復原資料庫。

### 驗證方式

- 在支援的 SQLite／作業系統組合測試資料表初始化、CRUD、索引、刪除及搜尋。
- 以 mock／虛構資料同時測試 FTS5 和 `LIKE` 路徑。
- 使用固定、虛構的時區測試案例驗證一般日期、夏令時間切換與缺少時區資料時的錯誤處理。
- 若有 schema 變更，先以測試資料演練「備份 → 遷移 → 驗證 → 還原」，並檢查記錄中沒有資料內容。

### 回滾方式

- SQLite 能力診斷可隨程式版本回退，不應改變 schema。
- 若只調整平台文件，回退文件即可；不要因此新增非必要套件。
- 若已執行資料庫遷移，只有在已驗證備份可還原時才回退應用程式；若還原未通過，停止部署並採取資料庫復原程序，不能以程式碼回退掩蓋資料狀態。

### 階段出口

- 搜尋在 FTS5 可用與不可用時都有可接受且可測試的行為。
- 支援平台的時區資料取得方式明確。
- schema 若有變更，升級與還原都已在隔離資料上演練成功。

## 階段 3：選用郵件與 Agent CLI 的版本治理

### 變更

- 將 `gog`、`gsk` 及操作者選用的 Agent CLI 視為獨立相依，建立「已測版本／未驗證版本」記錄。
- 先確認各工具是否提供穩定版本查詢及相容性承諾；必要時提出最低支援版本或已測版本範圍，不直接自動更新。
- 將各 CLI 的相容性測試與核心 Python 升級分離；以假的程序、mock 輸出或本機測試替身驗證解析和錯誤處理。
- 保持密碼、API key 等值不進 repo、文件、命令輸出或測試；不改任何憑證設定。

### 相容性風險

- CLI 參數、輸出格式、認證流程與錯誤訊息可能隨版本改變。
- CLI stderr 或上游回應可能包含敏感內容；測試與診斷應只保留已遮罩、經正規化的結果。
- Agent 驅動本來就可能把 context pack 送往外部；任何驗證都不得誤觸正式外部端點。

### 驗證方式

- 以 mock 子程序或本機假服務覆蓋成功、逾時、非零結束碼、格式錯誤與空回應。
- 使用明顯假值作為測試憑證，只驗證環境變數名稱與傳遞流程；測試不得呼叫正式服務。
- 檢查錯誤訊息、測試報告及 log 不包含原始程序輸出、信件內容或憑證值。
- 每種外部 CLI 升級各自執行整合測試，不以核心單元測試通過推論 CLI 相容。

### 回滾方式

- 回復到前一個已測 CLI 版本，或停用該選用驅動並使用現有本機後備；不回退 Python／SQLite 階段。
- 若升級涉及操作者本機工具，保存升級前的工具版本資訊與設定備份；不得在回退說明中記錄憑證值。

### 階段出口

- 每個選用 CLI 有清楚的測試版本、相容性狀態與停用／回退方式。
- 核心在選用 CLI 缺席或失敗時仍能按既有設計運作。

## 階段 4：瀏覽器與可選前端檢查工具

### 變更

- 決定並記錄支援的桌面與行動瀏覽器範圍，特別確認 JavaScript、service worker 及安全內容需求。
- 若保留 Node.js 為選用開發工具，明訂建議測試版本並確認缺少 Node 時核心 Python 測試仍可執行。
- 除非另有核准，不新增 npm 執行期依賴、前端建置流程或必要 Node 安裝。
- 需要調整瀏覽器相容程式碼時，限定為單獨變更並維持繁中／英文 UI 回歸檢查。

### 相容性風險

- 瀏覽器版本差異可能影響 PWA、service worker、模組載入與通知 API。
- 自動化瀏覽器測試可能依賴 Node、瀏覽器驅動或特定 headless 環境，不能讓可選工具成為使用者啟動門檻。
- 舊版瀏覽器可能不支援新的語法或 API。

### 驗證方式

- 對已核准的瀏覽器矩陣執行本機 UI smoke；使用虛構資料，不載入真實信件。
- 執行 `node --check`（若 Node 可用）及 UI 基本語言切換、窄螢幕、PWA 資源測試。
- 確認 service worker 不快取 `/api/*`，且未加入外部網路請求。
- 確認缺少 Node 時，核心伺服器與 Python 測試仍可使用。

### 回滾方式

- 回退 UI 程式碼與瀏覽器支援宣告；不改 Python 或資料庫。
- 若新檢查工具造成安裝或 CI 阻塞，撤回該工具整合並保留既有可選檢查方式。

### 階段出口

- 最低瀏覽器支援範圍可測試，PWA 與核心 UI 通過本機回歸。
- Node/npm 若仍是可選工具，不會變成安裝或執行的必要條件。

## 階段 5：分批發布與支援政策收斂

### 變更

- 將已驗證的 Python、SQLite／時區、外部 CLI 與瀏覽器變更拆成可獨立審查的提交或發布，不同類型升級不混成單一大變更。
- 更新支援版本、已測組合、棄用期限及回退說明。
- 先在隔離環境及複製測試資料上驗證；如需真實使用者試行，必須另有明確授權、資料保護方案與獨立發布決策。
- CI 版本矩陣若需要改 workflow，另案提出，不在本計畫中預先修改。

### 相容性風險

- 多個執行環境同時變更會使故障來源難以定位。
- 舊版 Python 停止支援會影響仍未遷移的操作者。
- 資料庫遷移與應用程式回退若不同步，可能使舊版程式無法讀取新版資料。

### 驗證方式

- 每個發布單位都執行其目標版本的完整 unittest、smoke、SQLite 與時區測試。
- 檢查版本宣告、安裝檢查、部署說明及實際支援政策一致。
- 核對回退演練結果、資料庫備份驗證結果及未覆蓋環境。
- 發布前確認沒有新增 secrets／憑證設定、外部服務呼叫或未核准的工作流程變更。

### 回滾方式

- 逐項回退最後一個未通過驗收的變更，不一次撤回已驗證的無關升級。
- 無資料格式變更時回到前一個已測版本。
- 有資料格式變更時先依演練流程還原升級前資料，再回退應用程式；還原前先停止寫入，避免新舊資料狀態混用。
- 將未能回退的環境及原因列為發布阻擋事項，不以「降級後再觀察」取代資料驗證。

### 階段出口

- 支援政策與文件一致，所有已宣布支援的平台都有測試證據。
- 未完成環境、外部 CLI 版本或回退演練均明確列出，不宣稱全面相容。

## 建議執行次序

1. 先完成階段 0，取得實際版本與資料遷移基線。
2. BOB 核准 Python 最低支援版本後才進行階段 1。
3. 階段 2 確認平台差異與復原程序；不預設新增 pip 相依或 SQLite 最低版本。
4. 階段 3 的 CLI 驗證與 Python 核心升級分開進行。
5. 階段 4 先定義瀏覽器支援政策，再決定是否增加可選檢查工具。
6. 階段 5 逐項發布；任何 workflow 變更另案審批。

## 需要 BOB 決策

| 決策 | 保守建議 | 需確認的影響 |
|---|---|---|
| Python 最低版本 | 將目標訂為 Python 3.11 以上；升級前先盤點部署者現況 | 停止支援 Python 3.9 會要求部分使用者升級直譯器；若 CI 矩陣需同步修改，需另案授權 |
| Python 測試矩陣 | 最低支援版本加一個較新的受支援版本 | CI workflow 目前內容未提供；改動 workflow 必須另案處理 |
| SQLite 最低版本 | 暫不提高最低版本，保留 FTS5／`LIKE` 雙路徑 | 若大型資料集效能不足，再以量測結果決定是否提高要求 |
| 時區資料 | 優先使用平台提供的 IANA 資料，不新增必要 pip 套件 | 不同作業系統的安裝說明與容器基底可能需要分開維護 |
| 外部 CLI 版本 | 先記錄已測範圍，不自動更新 | 是否設定最低版本、固定版本或由使用者自行維護 |
| 瀏覽器支援範圍 | 先指定可驗證的現代瀏覽器版本，不承諾未測平台 | 舊瀏覽器是否繼續支援，以及是否接受選用 UI 自動化工具 |
| 第三方套件政策 | 核心維持零 pip／零 npm 執行期相依 | 若未來引入任何必要套件，需另做供應鏈與版本鎖定決策 |

# Openinbox 路線圖

## 1. 路線圖定位

現有 `STATE.md` 已將 38 項 GenMail 對齊功能標記為完成，因此下一階段不應再以「補齊表面功能」為主，而應依下列順序提升實際使用價值：

1. 先確保本機資料不會遺失或彼此不一致。
2. 再提高同步、搜尋與外部 Agent 的可觀察性與可用性。
3. 接著處理多 mailbox、規則、行事曆與批次操作等高頻維運需求。
4. 最後強化無障礙、效能與外掛治理。

以下排序是價值排序，不是只按實作難度排序。估計以一名熟悉目前程式碼的工程師計算單位為「人日」，包含測試與文件，不包含產品決策等待時間。

## 3. 詳細項目

### 1. 本機資料備份、還原與完整性檢查

**價值**

目前郵件、人格、Second Brain、草稿、聯絡人、技能設定、outbox 與用量資料分散在 SQLite 和多個本機檔案中，程式沒有內建備份與還原流程。這是本機優先產品最直接且最高的資產保護缺口。

**建議範圍**

- 以 SQLite 備份 API 或停止服務後的檔案快照建立一致備份，避免直接複製仍在寫入的資料庫。
- 備份 `data/`、`vault/`、必要的本機設定與 `rules.json`。
- 產生不含郵件內容明文的 manifest，記錄檔案雜湊、大小、版本與建立時間。
- 提供 `backup`、`verify`、`restore --dry-run` 與受保護的實際還原流程。
- 還原至隔離的暫存根目錄，驗證成功後才允許覆蓋現有資料。
- 明確區分「一般本機資料」與「含環境變數名稱、帳號設定的設定檔」。
- 不把任何憑證值寫進備份；是否加入 passphrase 加密作為獨立決策項。

**驗收條件**

- 可在乾淨暫存根目錄完整還原，並驗證郵件、草稿、卡片、聯絡人與設定數量。
- 備份期間資料庫仍一致，無損毀或缺頁。
- manifest 可偵測缺檔、損毀與不相容版本。
- 還原預設先 dry-run，不直接覆蓋。
- 測試使用暫存目錄與假資料，不會讀寫開發者正式設定。

**主要風險**

- 在服務執行時直接複製 SQLite 可能造成不一致。
- 加密會引入金鑰遺失與復原複雜度。
- 設定檔可能含帳號地址等敏感中繼資料，備份必須加密或限制存取。

### 2. 快取、摘要與衍生資料一致性

**價值**

目前郵件更新後，舊的 triage 摘要、Agent 結果、Second Brain 卡片與搜尋索引何時失效並未形成完整的一致性契約。使用者可能看到已過期摘要，搜尋結果也可能短暫落後。

**建議範圍**

- 為郵件內容、附件存在、已讀狀態、分類與 thread 關係建立穩定版本簽章。
- 郵件內容或重要 metadata 改變時，使對應摘要失效並重新計算。
- 對 Agent 結果快取記錄來源簽章；來源改變時不得直接沿用。
- 將搜尋文件、Second Brain 卡片與人格的更新觸發統一成可重入的衍生流程。
- 清理快取與重新播種時，衍生結果必須可重現。
- 對衍生失敗提供隔離狀態，不讓單一壞卡阻塞整個索引。

**驗收條件**

- 修改郵件本機快取後，相關摘要會標示過期或自動重算。
- 搜尋索引在同步後能搜尋新內容，且搜尋不到已刪除內容。
- 卡片與人格的更新順序可重入，不會重複卡片。
- 加入測試證明舊來源簽章不會命中新內容。

**主要風險**

- 簽章若包含不穩定欄位，可能造成不必要的重算。
- 衍生流程若與同步同時執行，需處理 SQLite 寫入競爭。

### 3. 供應商同步診斷與帳號設定整合

**價值**

live 模式最常見的問題不是核心功能缺失，而是使用者不知道缺少密碼、CLI 未安裝、帳號需重新認證，或某個資料夾無法讀取。把這些資訊集中到帳號設定，可顯著降低停機時間。

**建議範圍**

- 在帳號設定頁整合 driver、環境變數名稱、上次同步時間、同步結果與未讀數。
- 明確區分「缺少環境變數」「CLI 不存在」「CLI 認證失敗」「網路或 TLS 失敗」「帳號拒絕」。
- 保留現有「測試連線」：IMAP 只執行登入與 `EXAMINE`。
- 顯示最近一次同步耗時，但不記錄郵件主旨、寄件人或內文。
- 支援安全的重試與逐帳號重新整理，不讓單一帳號阻塞全部同步。
- 將中繼資料診斷與完整同步分開，讓診斷本身不觸發大量資料下載。

**驗收條件**

- UI 與 `/api/providers` 對同一狀態顯示一致。
- 缺少密碼時只顯示環境變數名稱，不顯示值。
- 診斷記錄不含郵件內容或憑證。
- 本機假 IMAP 與假 CLI 測試覆蓋各主要錯誤類型。

**主要風險**

- 上游 CLI 的錯誤文字可能不穩定或含有敏感內容，應先正規化再顯示。
- 不能因診斷功能而改成未經確認的憑證測試或 mailbox 寫入。

### 4. 擴充 MCP 唯讀工具與能力協商

**價值**

目前 MCP 只有收件匣、看板、搜尋 Brain、人格與存草稿五個工具。外部 Agent 無法直接使用成熟的自然語言搜尋與聯絡人 API，操作流程仍需繞回 HTTP。

**建議範圍**

- 先新增 `search_mail`、`list_contacts`、`get_contact` 等唯讀工具。
- 在 `tools/list` 回報工具版本與能力旗標，讓舊客戶端能安全忽略新欄位。
- 沿用本機 context pack 與語系，不把完整資料集一次傳給 MCP 客戶端。
- 對搜尋結果限制數量並使用既有本機索引。
- 保持 `save_draft` 為唯一寫入工具。
- 補齊 initialize、tools/list、tools/call、ping 與錯誤格式的協定測試。

**驗收條件**

- 新工具在 stdio MCP 中可被發現並正確回傳。
- 不存在任意檔案讀取、路徑穿越或額外寄送能力。
- 舊版 MCP 客戶端仍能使用既有五項工具。
- 測試使用暫存根目錄與虛構資料，不呼叫外部 Agent。

**主要風險**

- MCP 客戶端可能尚未理解新能力欄位，因此必須保持向後相容。
- 搜尋結果若沒有分頁或數量上限，可能造成單次回應過大。

### 5. IMAP 多 mailbox 與 modified UTF-7

**價值**

目前標準 IMAP 帳號主要使用預設 `INBOX`。許多使用者將收件、客戶、通知或封存信件分散在多個資料夾；部分伺服器也使用非 ASCII 資料夾名稱。

**建議範圍**

- 允許帳號設定 `mailboxes` 清單，而不是只接受單一字串。
- 顯示各 mailbox 的連線、同步、數量與錯誤狀態。
- 對資料夾名稱實作 modified UTF-7 編解碼。
- 保留 `EXAMINE`、`BODY.PEEK` 的唯讀原則。
- 為每封信保留來源帳號與 mailbox 資訊，避免同名資料夾互相覆蓋。
- 提供啟用、停用個別 mailbox 的方式。

**驗收條件**

- 本機假 IMAP 測試證明只發出 `EXAMINE`、`UID SEARCH`、`UID FETCH` 等唯讀命令。
- ASCII 與非 ASCII mailbox 名稱都能穩定同步。
- 移除一個 mailbox 只影響該來源，不刪除其他帳號資料。
- 密碼仍只來自環境變數。

**主要風險**

- 各 IMAP 伺服器對 LIST、特殊資料夾與編名的支援不一致。
- 多資料夾會放大同步量，需要節流與可見的增量策略。

---

### 6. 規則預覽、交易式套用與撤销

**價值**

規則可以自動標籤、封存、建立任務或產生草稿。既有 dry-run 是良好基礎，但批量套用後若結果不符，仍缺少安全復原機制。

**建議範圍**

- 套用前顯示符合的信件清單、欄位差異與預計動作，但不在預覽中暴露不必要的內文。
- 以單一交易套用同一批規則，避免只套用一半。
- 建立有限時間的撤销紀錄，支援還原本機標籤、資料夾、任務與自動草稿。
- 記錄規則版本、觸發時間與來源。
- 禁止規則直接寄信；維持人工確認原則。
- 對互相衝突的規則提供確定性優先序。

**驗收條件**

- 規則先 dry-run 再套用的流程有端到端測試。
- 批次執行中發生錯誤時可完整回滾。
- 撤销能還原受影響欄位，且不碰到非本批次的變更。
- 所有預覽與紀錄不含憑證。

**主要風險**

- 郵件在規則執行期間可能又被同步或人工修改，撤销需記錄基準版本。
- 過長的撤销保留期會增加資料量。

---

### 7. 行事曆 feed 增量更新與衝突處理

**價值**

目前支援匯入同事 ICS 與 free/busy，但 feed 重複匯入、遠端 UID 變更、本機事件與 feed 事件衝突時，需要更明確且穩定的更新規則。

**建議範圍**

- 以 feed 來源與事件 UID 建立穩定識別碼。
- 支援增量重抓與本地 ETag／last-modified；上游不支援時退回完整匯入。
- 在更新前比較摘要、開始／結束時間、RSVP 與取消狀態。
- 區分「使用者建立的本機事件」與「遠端 feed 事件」，避免更新 feed 時覆寫本機資料。
- 對重複 UID、缺少 UID、時區缺失與無效日期提供明確診斷。
- 邀請草稿仍維持本機狀態，不因 feed 更新而寄出。

**驗收條件**

- 同一 feed 重複更新不會產生重複事件。
- 遠端事件取消或改期能在下次更新正確反映。
- 本機事件不會被 feed 更新誤刪。
- ICS 測試使用完全虛構的日期與 UID。

**主要風險**

- 外部 feed 可能不提供穩定 UID 或只支援完整下載。
- 時區與全天事件跨地區更新時容易產生邊界錯誤。

---

### 8. 郵件批次操作與有限撤销

**價值**

大量整理收件匣需要重複點擊標星、封存、移動或標為已讀。批次操作可顯著降低日常整理成本，但必須避免誤套用到大量信件。

**驗收條件**

- 可依目前條件、帳號、分類或明確勾選清單執行。
- 操作前顯示數量與影響範圍，支援分批處理。
- 套用後在限定時間內可撤销。
- 批次操作不會觸發寄信、永久刪除或未預期的遠端變更。
- 對部分失敗提供逐項結果與重試建議。

**主要風險**

- 大批次會造成 SQLite 寫入鎖定與 UI 延遲。
- 批次期間同步新增的信件不應被意外納入。

---

### 9. 無障礙、鍵盤與大型資料集效能

**價值**

收件匣是每日密集使用的工具。鍵盤、螢幕閱讀器、窄螢幕與大量郵件若不穩定，會直接降低核心功能價值。

**建議範圍**

- 為收件匣、thread、抽屜、表格與對話框補齊語意、ARIA 狀態與 focus 管理。
- 統一鍵盤操作，確保輸入框內不會誤觸全域快捷鍵。
- 以 760 像素以下的手機版作為持續回歸基準。
- 針對數千至數萬封信件量測列表、搜尋、分類與摘要批次。
- 使用虛擬列表或分頁載入，避免一次渲染全部 DOM。
- 保留所有介面字串的繁中／英文鍵集合檢查。

**驗收條件**

- 核心流程可只用鍵盤完成，且焦點不會落到不可見元素。
- 自動檢查可抓到未標示的控制項與互動元素。
- 大型本機資料集下，列表操作維持可接受互動延遲。
- UI 測試仍可跳過缺少 Node.js 的環境，但核心 Python 測試不可依賴瀏覽器。

**主要風險**

- 虛擬列表可能破壞既有深連結、列印與鍵盤定位。
- 效能優化若快取太多 DOM 資料，可能增加瀏覽器記憶體使用。

---

### 10. 外掛清單、啟動診斷與版本治理

**價值**

Python 功能檔會在啟動時自動載入。任何語法錯誤、缺少依賴、路由衝突或版本不相容，都可能讓單一功能無法使用。明確清單可降低啟動失敗的診斷成本。

**建議範圍**

- 為每個功能模組提供名稱、版本、需求 Python 版本、提供的路由與 UI 模組 metadata。
- 啟動時檢查重複路由、缺少 UI 檔、格式錯誤與不安全 metadata。
- 在 `/api/features` 顯示健康狀態、最後錯誤與可操作訊息，但不得顯示郵件內容或完整環境。
- 允許在設定中停用損壞的外掛，讓其餘核心功能繼續運作。
- 保留「Python 外掛為受信任程式碼」的明確警告；不要宣稱是沙箱。
- 為外掛與核心版本建立相容矩陣。

**驗收條件**

- 故意加入暫存測試用的損壞模組時，服務仍可啟動並在功能清單顯示錯誤。
- 停用損壞外掛不需要修改核心檔案。
- 路由衝突可在啟動時被偵測。
- 不引入 pip 或外部套件管理流程。

**主要風險**

- metadata 若要求手動同步，可能反而增加維護負擔。
- 「自動停用」可能讓使用者誤以為功能只是暫時失敗，必須清楚顯示原因。

## 4. 建議里程碑

### 里程碑 A：本機安全與正確性

包含第 1、2、3、4 項，約 17–27 人日。

退出條件：

- 資料可一致備份、驗證與 dry-run 還原。
- 摘要、搜尋與衍生卡片不會長期使用過期來源。
- 帳號同步錯誤可在本機介面清楚診斷。
- MCP 新舊客戶端均維持相容。

### 里程碑 B：多來源與維運能力

包含第 5、6、7、8 項，約 23–39 人日。

退出條件：

- 多 mailbox 與非 ASCII 資料夾可穩定同步。
- 規則可預覽、交易式套用與撤销。
- feed 更新不重複、不覆寫本機事件。
- 批次操作可取消且可有限撤销。

### 里程碑 C：使用品質與外掛治理

包含第 9、10 項，約 11–19 人日。

退出條件：

- 核心流程具備可驗證的鍵盤與螢幕閱讀器支援。
- 大型本機資料集通過效能基準。
- 損壞外掛可被診斷與停用，不拖垮核心服務。

## 5. 所有項目的共同完成定義

每一項都必須符合以下條件才視為完成：

1. 不新增預設寄信路徑，不允許 Agent 繞過人工確認。
2. 不新增遙測、託管依賴或必要 pip 套件。
3. 所有測試使用 `tempfile`／`tmp_path` 與虛構資料，不連正式服務。
4. 測試憑證只用明顯假值，不使用任何真實 token、金鑰或密碼格式。
5. 新 API 先採向後相容方式；破壞性變更需獨立版本規劃。
6. 資料庫變更採可回復、可驗證的遷移。
7. 補齊 `unittest`、必要的 UI 語法檢查與 smoke 回歸。
8. 文件同步更新，且執行步驟以實際程式行為為準。
9. 錯誤訊息不得包含郵件內文、案件資料、憑證或外部端點原始回應。
10. 每次提交都不得修改 secrets、憑證設定、Git remote 或正式部署流程。

## 6. 決策閘門

以下不阻擋文件與安全準備工作，但實作對應項目時需要採保守預設：

| 決策 | 保守預設 | BOB 可選擇的方向 |
|---|---|---|
| 備份是否預設加密 | 先提供本機 manifest 與權限保護，不保存任何 passphrase | 預設 passphrase 加密、僅磁碟層加密，或由外部金鑰管理服務注入 |
| MCP 是否加入行事曆 | 第一階段只做搜尋與聯絡人等低風險唯讀工具 | 加入唯讀行事曆快照；不提供寄送或修改 |
| 規則撤销期限 | 採短期限、只保留 metadata 與必要狀態 | 延長期限，但接受更多本機資料與磁碟占用 |
| Python 外掛隔離 | 視為受信任本機程式碼，不宣稱沙箱 | 要求簽章、允許清單或獨立程序執行 |
| 未來寄信能力 | 維持排除，不列入本路線圖 | 若日後另立專案，需獨立安全審查與人工確認設計 |

## 7. 不建議現在做的事

- 不建議優先打造新的託管模型或付費點數層，這會偏離本機優先定位。
- 不建議先做大量視覺重構；在資料一致性與備份完成前，視覺重構的邊際價值較低。
- 不建議在本路線圖中直接加入自動寄信、郵件刪除或無人工確認的規則動作。
- 不建議用真實郵件、真實 Agent 或正式 IMAP 伺服器做自動測試。
- 不建議把 Python 外掛描述成安全沙箱；先建立信任與治理邊界即可。

# openinbox 程式碼審查報告

> 審查方式：以本次提供的工作樹快照、檔案清單、狀態文件與既有測試名稱進行靜態審查；未連線正式服務，未執行外部模型或信箱操作。

## 1. 結論

本次共整理 **22 項具體問題**：

| 嚴重度 | 數量 | 摘要 |
|---|---:|---|
| Critical | 0 | 已提供內容中未確認可直接造成遠端任意執行或正式寄送的路徑 |
| High | 6 | 本機資料遺失、錯誤觸發、live 模式混入示範資料、非預期對外同步 |
| Medium | 13 | 原子性、錯誤處理、輸入邊界、測試隔離、相依與可維護性風險 |
| Low | 3 | HTML 語意、冗餘程式碼、狀態文件漂移 |

「沒有 Critical」只代表本快照未確認 Critical，**不代表其餘 147 個僅有檔名或部分內容的檔案已經安全**。核心 HTTP、資料庫、郵件傳輸、搜尋、outbox 與大部分測試仍需補做內容級審查。

## 2. 審查範圍與限制

- 已逐檔盤點 repository 提供的 169 個檔案；詳見 [coverage.md](coverage.md)。
- 完整內容審查優先放在本快照實際提供內容的模組。
- 僅有檔名或狀態文件可佐證者，標為「待補內容審查」，不以推測冒充已確認缺陷。
- 未執行 `unittest`、瀏覽器測試、正式 IMAP/Gmail/模型服務或任何寄送路徑。
- 所有修補建議均維持「本機優先、預設不寄信、測試不連正式服務」的既有原則。

## 3. 嚴重度定義

| 嚴重度 | 判定準則 |
|---|---|
| Critical | 可直接導致遠端任意執行、未授權資料外洩、正式寄送或完整機密外洩 |
| High | 可能造成資料遺失、錯誤郵件處理、live/demo 資料混用或非預期對外操作 |
| Medium | 局部錯誤、重試困難、測試不穩定、相依脆弱或安全邊界不明 |
| Low | 可讀性、語意一致性、文件漂移或維護成本問題 |

## 5. 建議实施順序

1. 先處理 F-03、F-05、F-06、F-12，避免錯誤資料或非預期連線。
2. 再處理 F-01、F-02、F-04，建立本機資料的寫入一致性基礎。
3. 接著處理 F-07、F-08、F-18，統一分派與外部 driver 契約。
4. 最後處理 UI、smoke、測試與文件漂移。

## 6. 保守決策

- 維持預設不寄信，且不新增任何寄送路徑。
- `overnight` 的預設行為採最保守方案：只使用本機快取。
- live 模式不載入任何 demo fixture。
- 本機郵件、persona、brain 與 deliverable 一律視為敏感資料。
- 外部 CLI/HTTP/OpenAI-compatible driver 維持明確 opt-in；不得默認繼承整份正式環境。
- 不以「已有測試名稱」推論實作正確；核心測試需補內容級審查。

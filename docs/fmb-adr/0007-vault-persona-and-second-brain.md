# ADR 0007：vault：persona 與 Second Brain 的檔案式記憶

- 狀態：已接受（回溯整理）
- 相關程式：`server/persona.py`、`server/second_brain.py`、`vault/`（`.gitignore` 內，僅保留 `vault/cards/.gitkeep`）、`server/features/email_brain.py`

## 背景

「更了解你」與「第二大腦」是這個產品的核心體驗：它要記得你怎麼寫信、你在意什麼、你和誰在談什麼。
這些內容比信件快取更貼近個人，而且使用者會想**自己打開看、自己備份、必要時自己刪**。
把它們鎖在資料庫裡，會讓「這是我的東西」這件事變得模糊。

## 決策

1. 人格存 `vault/persona.json`（程式用）＋ `vault/persona.md`（人可讀），由 `server/persona.py` 重建；資料來源是信件、看板與（示範模式的）種子。
2. 第二大腦卡片存 `vault/cards/*.md`，索引存 `vault/index.json`，由 `server/second_brain.py` 重建；卡片可從信件、行事曆與 agent 產出蒸餾。
3. `vault/` 除了 `.gitkeep` 之外**全部 gitignored**：這是真實個人資料，不進 repo。
4. 使用者的**修正**（例如「這個人其實是客戶」）存在資料庫的修正表，重建時疊在推論結果上，且會在 prompt 裡標成「使用者已修正」；這樣重建不會把使用者的意見洗掉。
5. 檔案式記憶是**重建式**的：重建會覆蓋推論內容，但不覆蓋使用者的修正與自己寫的筆記。

## 取捨

**我們放棄**

- 交易與併發保護（檔案沒有 row lock）；資料量大時的查詢效率（卡片搜尋是簡單字串比對）。
- 集中式 schema：改格式要靠程式自己相容。

**我們得到**

- 使用者可以 `cat`、`grep`、丟進自己的筆記系統、整包備份。
- 記憶是可解釋的：每個推論都能追到來源信件或使用者修正。

**已知代價**

- `persona.md` 是產生物，手改會被下一次重建蓋掉；持久意見要走修正表。
- 檔案數量與 `index.json` 會隨時間長大，需要重建／清理機制。

## 後果

- **絕對不要**把 `vault/` 的內容 commit、貼進 issue／PR／文件，或放進測試 fixture（測試一律用暫存根目錄自己造資料）。
- 新增「記憶類」功能時，先問：這是推論（可重建、可覆蓋）還是使用者的主張（要保留、要顯示為「已修正」）？
- 卡片檔名／id 要正規化（`second_brain._slug` 是參考），避免路徑問題與同名覆蓋。
- 文件與範例只能用虛構人名與 `example.com` 網域。

# ADR 0011：成果卡片存檔案（deliverables）

- 狀態：已接受（回溯整理）
- 相關程式：`server/features/agents.py`（`save_deliverable`／`list_deliverables`／`read_deliverable`）、`ui/modules/agents.js`、`data/deliverables/`（gitignored）、技能輸出的 `data/slides/`

## 背景

代理協作會產出「東西」：人物研究、公司研究、會議準備、投影片。
這些產出使用者會想留存、匯出、貼到別的地方，也可能想直接看。
存進資料庫只能透過 API 取用；存成檔案則可以備份、可以被其他工具吃掉，也符合這個專案「檔案即資料」的調性。

## 決策

1. 每次產出寫三個檔：`data/deliverables/<id>.md`、`.html`、`.json`。
   - `.md` 給人看與複製；`.html` 給瀏覽器預覽；`.json` 是列表用的 metadata。
2. **id 先驗證再組路徑**：由 `kind` + slug + 時戳產生，並以嚴格的正規表示式檢查（長度、字元集），避免路徑穿越。
3. `.html` **全轉義**：沒有 script、沒有外部資源、沒有行內事件處理；UI 以 `sandbox` 的 iframe 預覽。
4. 列表只讀 `.json` 的 metadata，依時間排序並有上限，避免一次掃爆目錄。
5. 同一模式套用到其他產出物（例如技能產生的投影片放 `data/slides/`），保持一致的心智模型。
6. 卡片只放**摘錄**（來源 snippet 有長度上限），不要把整封信原封不動倒進檔案。

## 取捨

**我們放棄**

- 資料庫查詢能力（沒有 SQL 過濾、沒有全文搜尋、只有排序與上限）。
- 單一檔案打包（三種格式要一起維護，內容必須一致）。

**我們得到**

- 產出可攜、可備份、可直接用瀏覽器開；錯誤時也容易人工檢查。
- 沒有資料庫也能工作（例如只跑 CLI 的工作流）。

**已知代價**

- 檔案會累積，需要使用者自己清理（目前沒有自動輪替）。
- 檔名由內容推導，同一個對象會有多份卡片（以時戳區分，屬預期行為）。

## 後果

- 任何「由使用者輸入組出檔名」的新功能，都必須照這個模式：正規化 → 驗證 → 才組路徑；讀取端同樣驗證。
- 寫入前要確保目錄存在；讀取不到就回 404，不要把路徑或例外內容回給使用者。
- 卡片內容一律視為**本機資料**：不要上傳、不要放進 prompt 之外的第三方，也不要貼進 issue。

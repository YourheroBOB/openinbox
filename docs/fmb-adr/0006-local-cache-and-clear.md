# ADR 0006：本機快取與「可清除」契約

- 狀態：已接受（回溯整理）
- 相關程式：`server/yhbmail.py`（SQLite 與同步）、`server/features/cache.py`（`GET /api/cache`、`POST /api/cache/clear`）、`server/features/mailops.py`（本機狀態覆蓋）、`ui/modules/cache.js`

## 背景

信件**本體留在信箱供應商**，這台機器只放工作副本：正規化後的信件、分類結果、摘要、執行紀錄、衍生卡片。
使用者需要一個可信的承諾：「我按一下，這台機器上看過的內容就沒了。」
但「看過的內容」與「我自己創作的東西」必須分開——沒人希望清快取時把草稿清掉。

## 決策

1. 快取（可清）與使用者資產（不可清）**明確分開**，並落實在 `POST /api/cache/clear`：
   - **可清**：同步進來與衍生的資料，例如信件、行事曆事件、agent 執行紀錄（`agent_turns` 這類）、由信件蒸餾出的卡片。
   - **保留**：使用者創作的東西與設定，例如草稿、自己寫的筆記卡、匯入的同事行事曆（`cal_feeds`）、信件大腦的修正、任務與任務歷史、聯絡人 CRM、技能開關、用量紀錄。
   - 實際清單以 `server/features/cache.py` 的實作為準；README 雙語有對使用者的說法。
2. `POST /api/cache/clear` 可帶 `{"reseed": true}` 重新載入示範信；`GET /api/cache` 讓使用者先看清楚現在快取了什麼。
3. 清快取後，下次同步會重新抓（快取是**衍生物**，不是真相來源）。
4. 索引類資料（例如搜尋用的 FTS 表）跟著快取一起清，避免留下已刪信的內文。
5. UI 提供側欄按鈕，並在文案裡說明「草稿與你寫的筆記會保留」。

## 取捨

**我們放棄**

- 「清快取＝回到全新狀態」這種簡單心智模型；保留清單是人工維護的。
- 資料庫層級的統一清除（不同表有不同歸屬，必須逐一決定）。

**我們得到**

- 使用者敢按那個按鈕；也敢把真信箱接上來（配合 ADR 0008）。
- 快取失效的成本只是「再同步一次」。

**已知代價**

- 新增持久化資料時，一定要主動決定「這是快取還是資產」；漏了就會誤删或清了又回來。
- 保留清單分散在程式與 README，需要測試守著。

## 後果

- 新增資料表／檔案時，PR 必須說明歸屬，並更新 `server/features/cache.py` 與對應測試（`tests/test_tpi_foundation_cache.py` 是既有起點）。
- 任何「重建索引」「重建卡片」的程式要能被重複執行（idempotent），因為清快取後會再跑一次。
- 不要把使用者資產寫進快取目錄（`data/` 下仍要分清楚），否則清快取會波及。

# ADR 0002：不提供寄送路徑

- 狀態：已接受（回溯整理）
- 相關程式：`server/features/compose.py`、`server/features/outbox.py`、`server/features/_outbox_transport.py`、`server/agent_bridge.py`（`save_draft`）、`server/mcp_server.py`、`CONTRIBUTING.md`

## 背景

這個專案刻意對齊「AI 信箱助理」的功能面，但其中風險最高的就是**代替使用者發言**。
一旦有真的寄送路徑，就會牽涉到憑證權限、誤寄、agent 幻覺寫出承諾、以及測試不小心打到正式服務。
使用者原本的寄件備份與寄送能力都已經在自己的信箱供應商那裡，這個工具不需要重造。

## 決策

1. **程式庫不實作任何會離開這台機器的寄送。** 沒有寄送 API、沒有寄送佇列的傳輸層；`_outbox_transport.py` 是「本機邊界」而不是對外連線。
2. 撰寫（新信／回覆／轉寄）只產生**本機草稿**，存在本機 SQLite 的 drafts 表；面板可以預覽、編輯、複製。
3. Schedule／Undo Send 只做**本機 outbox**：排程佇列、倒數取消、到期後移到本機 outbox 資料夾，結束在那裡。
4. **寄出前一律人工確認**，而且「確認」的意義只是把草稿標成可帶走，不是把信送出去。
5. agent 工具集裡**沒有寄送工具**；`save_draft` 只寫本機資料列，回傳明確的 `sent: false`。
6. MCP 伺服器同樣只提供唯讀工具 + `save_draft`（ADR 0010）。
7. 列印／存 PDF 走 `/mailops/print` 產生 HTML，讓使用者用瀏覽器自己存。
8. 技能與 agent 的 `context_pack` 一律帶「唯讀、不要寄信、不要回覆邀請」這類規則；提示詞把信件內容視為**資料**而非指令。

## 取捨

**我們放棄**

- 「一鍵真的寄出」的爽感，以及由此而來的自動化流程（例如自動回覆、自動 RSVP）。
- 需要寄送權限才能實作的整合。

**我們得到**

- 誤寄風險為零；agent 不可能替使用者做出承諾。
- 測試與 CI 完全不需要網路，也不需要寄送憑證。
- 使用者可以放心把 IMAP 憑證交給它（見 ADR 0008）。

**已知代價**

- 使用者必須多做一步（把草稿複製到自己的客戶端）。
- 有些功能只能做到「準備好資料」，不能「完成動作」——這是刻意的。

## 後果

- 任何 PR 只要新增「會離開這台機器」的輸送（包含第三方 API、webhook、雲端寄送服務），就必須先開新 ADR，並同時更新 `CONTRIBUTING.md` 的規則。
- 新功能的終點只允許是：本機草稿、本機 outbox、本機成果卡片（ADR 0011）、本機檔案。
- 程式碼審查時，「send」相關字樣應理解為**本機狀態轉移**；若看到真的對外傳輸，視為違反本 ADR。
- 文件、issue、截圖都不得示範如何把草稿送出去。

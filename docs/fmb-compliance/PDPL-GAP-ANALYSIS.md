# 台灣個資法對照與缺口分析

本文件以《個人資料保護法》一般要求對照 openinbox 現況，列出缺口、風險等級與建議。條號以現行公布條文為準；適用性仍取決於使用情境（見 `README.md` 第 3 節）。

## 1. 條文對照總表

| 條文 | 要求（摘要） | openinbox 現況 | 缺口 | 優先級 |
|---|---|---|---|---|
| 第 1 條 | 規範蒐集、處理、利用，避免人格權受侵害 | 本機優先、不預設寄信、無遙測 | 無明顯缺口，但未成文宣示個資保護目的 | P2 |
| 第 2 條 | 定義個人資料、蒐集、處理、利用、國際傳輸、當事人、蒐集者、處理者 | 未定義角色（使用者＝蒐集者？BYO agent＝受託處理者？） | 角色與責任未釐清 | P0 |
| 第 3 條 | 當事人五項權利 | 無查詢／複本／更正／停止／刪除 API；僅能整批清快取 | **G2** | P1 |
| 第 5 條 | 利用應尊重當事人權益、誠實信用、比例原則 | 無保留期、無最小化設計說明；人格側寫持續累積 | **G3** | P1 |

| 第 29 條 | 違反本法致損害的賠償責任 | 無免責與責任限制說明 | **G16** | P2 |

## 2. 缺口明細

### G1 無隱私告知與角色釐清（第 2、8、9、19、51 條）— P0

**現況**：README 描述功能與資料位置，但沒有「蒐集者名稱、蒐集目的、個資類別、利用期間地區對象方式、當事人權利行使方式、不提供將造成的影響」等告知要素。也沒有說明使用者與 BYO agent 之間的角色關係。

**風險**：寄件人與與會者是第三人，若日後提供給他人使用或商業使用，第 8、9 條的告知義務難以主張已履行。

**建議**：
1. 採用 `PRIVACY-NOTICE-DRAFT.md` 的內容，於 README 或首次啟動頁顯示（需 BOB 決定放置位置）。
2. 明確寫出角色：使用者為蒐集者；BYO agent 與 MCP 客戶端營運者為受託處理者或獨立蒐集者（取決於其條款）。
3. 明確寫出第 51 條的適用前提：「僅限自然人為單純個人或家庭活動使用」。

### G2 當事人權利無行使管道（第 3、10 條）— P1

**現況**：只有整批清除；沒有依 Email 或 thread 查詢／匯出／刪除。

**建議**：實作 `GET /api/privacy/export` 與 `POST /api/privacy/erase`（見 `RETENTION-DELETION.md` R2／R3），並提供 15 日答覆的人工 SOP。

### G3 無保留期與最小化（第 5 條）— P1

**現況**：資料無限累積；人格側寫持續更新。

**建議**：依 `RETENTION-DELETION.md` 第 4 節設定保留期；對側寫資料提供「關閉學習」與「重設」。

### G4 刪除不完整（第 11 條）— P1

**現況**：`/api/cache/clear` 保留草稿、行事曆、使用者卡片；`data/deliverables/`、`data/slides/`、`data/usage.jsonl` 未列入 `[C]`；WAL 與 SQLite 未使用頁面可能殘留。

**建議**：補齊清除語意、加 WAL checkpoint 與可選 `VACUUM`、建立稽核紀錄。

### G5 跨境傳輸與委外監督（第 20、21 條，第 4 條第 5 款）— P1

**現況**：`agent.json` 的 `base_url` 可為任何端點；MCP 客戶端背後的雲端模型會取得工具輸出。沒有首次外送提示、外送記錄、端點白名單或 `allow_remote` 明確確認。

**建議**：
1. 非 loopback 端點需在 `agent.json` 設 `"allow_remote": true` 才生效，並在 UI 顯示「資料將離開本機」。
2. 首次外送前顯示一次告知（含資料類別與目的地網域）。
3. 僅記錄「外送事件」（時間、目的地 host、context pack 大小），不記錄內容。
4. 文件建議使用者與外部 Agent 營運者簽訂資料處理約定。

### G6 安全維護措施未成文（第 27 條、施行細則第 12 條）— P0

**現況**：技術面有多項良好實務，但缺少成文計畫與組織措施。

**建議**：
1. 撰寫「個人資料檔案安全維護計畫」（可放 `docs/fmb-compliance/`，需 BOB 決定最終位置）。
2. 明定檔案權限：`data/`、`vault/` 應為 `700`／`600`；`install.sh` 加 `umask 077` `[C]`。
3. 明定日誌政策（見 `LOGGING-REVIEW.md`）。
4. 明定備份加密與異地保存要求（對應 ROADMAP 第 1 項）。
5. 明定事故應變與通報（見 G13）。
6. 明定教育訓練與新功能合規檢查（本目錄的更新流程）。

### G7 受託處理者監督 — P1

**現況**：BYO agent、CLI、MCP 客戶端皆為外部處理者，無監督紀錄。

**建議**：在文件中列出「資料處理者清單」，說明各自可見的資料範圍與使用者應自行確認的條款。

### G8 特種個資與高敏感內容（第 6 條）— P1

**現況**：可能偶然快取病歷、財務、身分證字號等內容；無偵測、無提示。

**建議**：
1. 不建立任何以特種個資為對象的分析功能。
2. 提供「敏感內容提示」（僅提示，不自動刪除）。
3. 文件明示使用者不得以此工具大規模蒐集他人特種個資。
4. 測試與 fixtures 不得包含任何看起來像真實身分證號的字串；必要時用 `FAKE_VALUE_FOR_TEST`。

### G9 記錄與錯誤訊息（第 27 條技術措施）— P1

**現況**：`agents.py` 的 `error_label()` 是良好範例 `[A]`；但 HTTP 請求記錄、CLI stderr、`base_url`、搜尋查詢可能外洩 `[C]`。

**建議**：見 `LOGGING-REVIEW.md` 第 3–6 節。

### G10 資料正確性與可更正性（第 11 條）— P2

**現況**：`brain_fixes` 可修正推論（良好）；但郵件快取可能過期，人格推論可能錯誤且未標示為推論。

**建議**：在 UI 標示「本機推論」，提供一鍵更正；對郵件快取顯示最後同步時間（部分已有）。

### G11 第三方條款未確認 — P1

**現況**：`gog`、`gsk`、模型授權未確認（見 `DEPENDENCIES.md` L3）。

**建議**：商業使用前完成確認並寫回文件。

### G12 无（略）— 見 G13

### G13 事故應變與通知（第 12 條）— P1

**現況**：無外洩偵測、無通報流程、無事後改善紀錄。

**建議**：
1. 建立 `INCIDENT-RUNBOOK`（草案可放本目錄）：發現、隔離、影響評估、通知、改善。
2. 定義「需通知當事人」的門檻與通知範本。
3. 日誌需足以判斷影響範圍（誰的資料、哪些資料集），但不得含內容。

### G14 委外與跨境的紀錄（RoPA）— P2

**現況**：本目錄的 `DATA-INVENTORY.md` 即為簡化版處理紀錄。

**建議**：功能變更時同步更新，並在 PR 模板加「是否新增個資處理或外送路徑」的檢查項（需 BOB 決定是否改 `.github/`，本輪禁止修改）。

### G15 教育訓練與意識 — P2

**建議**：在 `CONTRIBUTING` 加「不得貼入真實郵件、帳號、憑證」與「新增外送路徑需更新合規文件」。

### G16 責任與用途限制說明 — P2

**現況**：`LICENSE` 為 MIT，含免責條款；但未提示不得用於不法蒐集他人個資。

**建議**：在 README 加「合法使用」段落（不改變 MIT 授權效力）。

## 3. 風險排序（建議處理順序）

| 順序 | 缺口 | 理由 |
|---|---|---|
| 1 | G1 告知與角色 | 是所有其他義務的前提；文件即可完成大部分 |
| 2 | G6 安全維護成文 | 成本低、效果大（權限、日誌、備份要求） |
| 3 | G5 跨境與委外 | 是目前最實質的外洩路徑 |
| 4 | G4 刪除完整性 + G2 當事人權利 | 需程式改動，但可先以人工 SOP 補位 |
| 5 | G8 特種個資 | 需設計，不宜草率自動處理 |
| 6 | G9 記錄遮罩 | 與 G6、G13 一起做 |
| 7 | G3／G10／G7／G11 | 治理與品質 |
| 8 | G13／G14／G15／G16 | 組織措施，可並行 |

## 4. 結論

openinbox 的架構在**技術面**已經具備多項隱私友善特性：本機優先、不預設寄信、唯讀 IMAP、憑證只從環境變數、錯誤訊息遮罩、Service worker 不快取 API。真正的主要缺口不在加密或傳輸，而在：

1. **沒有成文的告知與角色定義**（G1）。
2. **沒有保留期與完整的刪除路徑**（G3、G4、G2）。
3. **BYO agent 與 MCP 客戶端造成的外送缺乏可見性與同意機制**（G5）。
4. **安全維護措施與事故應變未成文**（G6、G13）。

上述四項若補齊，即使在商業使用情境下，也能顯著降低個資法風險。
